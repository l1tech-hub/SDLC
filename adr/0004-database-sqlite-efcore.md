# Для хранения данных используется SQLite с доступом через EF Core и миграциями

## Контекст и постановка задачи

SRS требует использовать базу данных (CON-4) и хранить продукты, блюда, составы и журнал во встраиваемой реляционной БД в одном файле, не требующей отдельного сервера (REQ-INT-004). Данные должны быть защищены от некорректных состояний: отрицательные остатки, дубликаты названий, ссылки на несуществующие продукты (REQ-SEC-001). Операции над несколькими записями должны быть транзакционными (REQ-REL-001). Первый запуск должен сам создавать пустую БД (REQ-INST-001).

Какую СУБД и какой способ доступа к данным использовать?

## Драйверы решения

* Встраиваемая БД в одном файле, без сервера и прав администратора (REQ-INT-004, REQ-INST-001).
* Ограничения целостности на уровне БД и транзакции (REQ-SEC-001, REQ-REL-001).
* Скорость разработки при малом объёме кода (один разработчик).
* Создание и обновление схемы без ручных скриптов (первый запуск, версия 2.0).
* Производительность на объёмах до 5000 продуктов и 500 блюд (REQ-PERF-001).
* Бесплатные лицензии (REQ-COST-001), совместимость с .NET 10 (ADR-0002).

## Рассмотренные варианты

* SQLite + EF Core (миграции)
* SQLite + Dapper / ADO.NET с ручным SQL
* LiteDB (встраиваемая документная БД)
* SQL Server LocalDB / Express
* Файлы JSON

## Итог решения

Выбранный вариант: «SQLite + EF Core (миграции)», потому что он удовлетворяет требованию встраиваемой реляционной БД в одном файле, поддерживает внешние ключи, `CHECK` и транзакции, а EF Core сокращает объём кода доступа и автоматически создаёт и обновляет схему.

Параметры: внешние ключи включены на каждом соединении; миграции применяются при запуске (создаётся пустая БД); режим журнала SQLite по умолчанию (rollback journal) и `synchronous = FULL` для максимальной надёжности записи на HDD (см. ADR-0006); короткоживущие контексты на операцию (`IDbContextFactory`).

### Последствия

* Хорошо, потому что БД — один файл, установка СУБД не нужна.
* Хорошо, потому что ограничения (`UNIQUE`, `FOREIGN KEY`, `CHECK`) защищают данные независимо от ошибок в коде.
* Хорошо, потому что миграции создают БД при первом запуске и пригодятся для изменений схемы в версии 2.0.
* Плохо, потому что у SQLite ограничены возможности изменения схемы (EF Core пересоздаёт таблицы при некоторых миграциях) — приемлемо для небольшой БД.
* Плохо, потому что у EF Core есть накладные расходы при первом обращении (прогрев модели): нужно держать запуск в пределах 5 с (REQ-PERF-002) — окно показывается сразу, БД инициализируется асинхронно.
* Плохо, потому что регистронезависимость для кириллицы средствами SQLite не работает — решается отдельно (ADR-0005).
* Плохо, потому что открытый файл БД нельзя просто копировать для резервной копии — решается через `VACUUM INTO` (ADR-0007).
* Плохо, потому что «блюдо без состава» нельзя запретить ограничением БД — проверяется сервисом внутри транзакции (SDD 5.3, DR-5).

### Подтверждение

* Интеграционные тесты `CafeCalc.Infrastructure.Tests` на реальном SQLite: попытки записать отрицательный остаток, дубликат `NameKey`, продукт с несуществующим внешним ключом, повтор продукта в составе блюда отклоняются БД.
* Тест миграций: применение к пустой БД создаёт ожидаемую схему; повторный запуск идемпотентен.
* Тест «перезапуск»: данные сохраняются после пересоздания контекста (критерий REQ-INT-004).
* Замеры по REQ-PERF-001 и REQ-PERF-002 на опорном ПК.

## Плюсы и минусы вариантов

### SQLite + EF Core (миграции)

* Хорошо, потому что встраиваемая реляционная БД в одном файле.
* Хорошо, потому что меньше шаблонного кода, миграции, LINQ.
* Нейтрально, потому что нужен ряд пакетов (`Microsoft.EntityFrameworkCore.Sqlite`), все с MIT-лицензией.
* Плохо, потому что накладные расходы EF Core и ограничения `ALTER` в SQLite.

### SQLite + Dapper / ADO.NET с ручным SQL

* Хорошо, потому что полный контроль над SQL и минимальные накладные расходы.
* Плохо, потому что больше ручного кода (маппинг, миграции схемы, повторяющиеся CRUD-запросы).
* Плохо, потому что выше риск ошибок и срок при единственном разработчике.

### LiteDB (встраиваемая документная БД)

* Хорошо, потому что один файл и простой API.
* Плохо, потому что нереляционная модель: нет внешних ключей и `CHECK`, целостность пришлось бы обеспечивать только кодом (REQ-SEC-001).
* Плохо, потому что требование SRS говорит о реляционной БД (REQ-INT-004).

### SQL Server LocalDB / Express

* Хорошо, потому что богатые возможности СУБД.
* Плохо, потому что требует установки СУБД на ПК кафе (нарушает REQ-INT-004, REQ-INST-001), LocalDB — только для Windows.
* Плохо, потому что избыточен для одного рабочего места.

### Файлы JSON

* Хорошо, потому что максимально просто.
* Плохо, потому что нет транзакций и ограничений целостности, атомарность записи нужно писать самому (REQ-REL-001), и это не БД (CON-4).

## Дополнительная информация

Связанные требования SRS: CON-4, REQ-INT-004, REQ-SEC-001, REQ-REL-001, REQ-INST-001, REQ-PERF-001, REQ-PERF-002, допущения A-1, A-6. Связанные представления SDD: 004-information, 010-deployment, 014-dependency. Связанные ADR: ADR-0005, ADR-0006, ADR-0007.

Пересмотреть решение, если: изменится допущение A-1 (несколько рабочих мест с одной БД) — потребуется серверная СУБД; объём данных существенно вырастет (порядка сотен тысяч записей).
