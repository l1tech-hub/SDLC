# Для интерфейса CafeCalc выбран WPF с паттерном MVVM (CommunityToolkit.Mvvm)

## Контекст и постановка задачи

CafeCalc — десктопное приложение для одного рабочего места кафе. SRS закрепляет язык C# (CON-1), разработку в JetBrains Rider (CON-2), десктопный формат (CON-3), русский интерфейс (CON-9), платформу Windows 10/11 (A-2, REQ-PORT-001) и модальные окна ввода (REQ-INT-001, CON-6). Интерфейс содержит списки до 5000 продуктов с миниатюрами, поиск по мере ввода, формы с проверкой ввода и горячие клавиши (REQ-INT-003).

Какой UI-фреймворк использовать, чтобы уложиться в требования при небольшой команде и ограниченных сроках?

## Драйверы решения

* Ограничения CON-1…CON-3 и работа из Rider.
* Срок и размер команды (один разработчик, учебный проект): низкий порог входа, мало шаблонного кода.
* Список с тысячами элементов и миниатюрами: нужны привязка данных и виртуализация (REQ-FUNC-001, REQ-PERF-001, REQ-PERF-002).
* Валидация ввода с показом ошибки у поля (REQ-FUNC-005, REQ-INT-002).
* Тестируемость логики представления без запуска окон (REQ-MAINT-001).
* Бесплатные лицензии (REQ-COST-001).
* Платформа только Windows (REQ-PORT-001) — кроссплатформенность не требуется.

## Рассмотренные варианты

* WPF + CommunityToolkit.Mvvm
* Windows Forms
* Avalonia UI
* WinUI 3
* .NET MAUI

## Итог решения

Выбранный вариант: «WPF + CommunityToolkit.Mvvm», потому что он лучше всех сочетает зрелую привязку данных, виртуализацию списков и встроенный механизм валидации (`INotifyDataErrorInfo`) с низким риском для небольшого проекта, а кроссплатформенность, ради которой стоило бы брать Avalonia, SRS не требует.

### Последствия

* Хорошо, потому что привязки и `ObservableValidator` позволяют показывать ошибки у полей почти без кода (REQ-FUNC-005).
* Хорошо, потому что виртуализация списка и ленивое создание миниатюр удерживают память в бюджете 300 МБ (REQ-PERF-002).
* Хорошо, потому что логика ViewModel тестируется модульными тестами без окон.
* Плохо, потому что приложение привязано к Windows; при смене допущения A-2 потребуется миграция на Avalonia (разметка схожа, но не идентична).
* Плохо, потому что возможности визуального конструктора в Rider скромнее, чем в Visual Studio: разметку XAML придётся писать вручную по макетам из SRS (приемлемо для ~9 простых окон).
* Нейтрально: добавляется зависимость CommunityToolkit.Mvvm (лицензия MIT, см. SDD 014-dependency).

### Подтверждение

* Код-ревью: code-behind содержит только код, связанный с представлением (например, установка фокуса); бизнес-логики и обращений к БД нет.
* Модульные тесты ViewModel (доступность команд, показ ошибок) в `CafeCalc.Core.Tests`.
* Проверка свойств проекта: `TargetFramework = net10.0-windows`, `UseWPF = true`.
* Демонстрация REQ-INT-001 (модальные окна блокируют главное окно) и REQ-INT-003 (горячие клавиши).

## Плюсы и минусы вариантов

### WPF + CommunityToolkit.Mvvm

Зрелый фреймворк для Windows-приложений с XAML, привязкой данных и шаблонами элементов.

* Хорошо, потому что привязка данных, шаблоны и виртуализация закрывают списки с миниатюрами.
* Хорошо, потому что `ObservableValidator` реализует показ ошибок у полей.
* Хорошо, потому что поддерживается Rider и работает на Windows 10/11 без доп. рантаймов (включается в самодостаточную поставку).
* Плохо, потому что только Windows.
* Плохо, потому что визуального конструктора в Rider почти нет — XAML вручную.

### Windows Forms

* Хорошо, потому что самый простой для небольших форм и быстро изучается.
* Нейтрально, потому что подходит для таких экранов без сложной кастомизации.
* Плохо, потому что слабее привязка данных и валидация, а списки с миниатюрами и виртуализацией требуют ручного кода.
* Плохо, потому что хуже тестируемость логики представления (MVVM не поддерживается «из коробки»).

### Avalonia UI

* Хорошо, потому что кроссплатформенный и XAML-подобный; снимает риск смены A-2.
* Нейтрально, потому что хорошая поддержка в Rider.
* Плохо, потому что кроссплатформенность не нужна (REQ-PORT-001), а экосистема и опыт меньше, чем у WPF.

### WinUI 3

* Хорошо, потому что современный внешний вид.
* Плохо, потому что тяжелее упаковка и зависимость от Windows App SDK, что усложняет простую установку копированием (REQ-INST-001).
* Плохо, потому что инструментальная поддержка вне Visual Studio слабее.

### .NET MAUI

* Хорошо, потому что единая кодовая база для нескольких платформ.
* Плохо, потому что ориентирован на мобильные платформы; для одной настольной Windows-программы избыточен и сложнее в настройке.

## Дополнительная информация

Связанные требования SRS: REQ-INT-001…003, REQ-PORT-001, REQ-PERF-002, REQ-COST-001. Связанные представления SDD: 002-composition, 005-interface, 009-patterns, 013-structure.

Пересмотреть решение, если: изменится допущение A-2 (потребуется Linux/macOS) или Заказчик запросит веб/мобильную версию.
