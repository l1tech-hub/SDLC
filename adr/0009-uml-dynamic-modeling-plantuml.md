# Динамическая модель системы строится в UML и хранится как PlantUML-код

## Контекст и постановка проблемы

В лабораторной работе №5 нужно описать динамику CafeCalc средствами UML: прецеденты, деятельность, последовательность и состояния. Диаграммы должны соответствовать стандарту UML, иметь ортогональные связи, храниться в Git рядом с кодом и меняться вместе с ним (SDD 1.1). SDD версии 0.1 содержал диаграммы в Mermaid, у которого нет полного набора обозначений UML (дорожки в диаграмме деятельности, фрагменты `break`, составные состояния с псевдосостоянием выбора, управление маршрутизацией линий).

## Факторы принятия решения

- соответствие нотации UML 2.5 (формы актёра, прецедента, узлов деятельности, фрагментов взаимодействия);
- ортогональные линии связей;
- текстовый формат, пригодный для diff и code review;
- бесплатность (REQ-COST-001);
- согласованность диаграмм друг с другом.

## Рассмотренные варианты

1. PlantUML (текст в `.puml`, рендер в SVG).
2. Mermaid (рендерится GitHub без доп. действий).
3. draw.io / Visio (графические редакторы).
4. Enterprise Architect / StarUML (CASE-средства).

## Решение

Выбран вариант 1: **PlantUML**, потому что он поддерживает нужные элементы UML, директиву `skinparam linetype ortho` для ортогональных линий и `skinparam style strictuml` для строгой нотации диаграмм последовательности, а исходники хранятся как текст. Mermaid оставлен для структурных диаграмм SDD (компоненты, ER, развёртывание), которые не входят в динамическую модель.

### Механизм построения диаграмм

Диаграммы строятся по цепочке, где каждый следующий артефакт опирается на предыдущий:

1. **Глоссарий** (`docs/glossary.md`) фиксирует имена, которые затем используются в подписях диаграмм.
2. **Диаграмма прецедентов** (`001`). Внешние события SRS превращаются в прецеденты, роль пользователя — в основного актёра, хранилище данных — во вспомогательного («База данных»). Повторяющееся поведение выносится в `<<include>>`, необязательное и условное — в `<<extend>>`.
3. **Текстовое описание прецедента** (`docs/use-cases.md`): предусловия, основной и альтернативные потоки, постусловия. Эти потоки — первичный источник для следующих диаграмм.
4. **Диаграмма деятельности** (`002`) строится из потоков одного прецедента: шаг потока — действие, альтернативный поток — ветвление, повтор ввода — цикл, роли «Сотрудник» и «CafeCalc» — дорожки.
5. **Диаграмма последовательности** (`003`) детализирует действия системы из диаграммы деятельности до уровня объектов SDD 003 и сообщений контрактов SDD 005: `ViewModel → Service → Validator/ImageStore/UnitOfWork`. Ветвления деятельности превращаются во фрагменты `alt`, `opt`, `break`.
6. **Диаграмма состояний** (`004`) строится по объекту, чьё поведение зависит от истории: панель списания (условия доступности элементов и результаты операции из UC-6).
7. **Бизнес-правила** (BR-*) из `docs/supplementary-spec.md` дают условия переходов и ветвлений (диапазоны, пороги).

### Связи между диаграммами

| Источник | Приёмник | Что переносится |
|----------|----------|-----------------|
| Прецедент (001) | Деятельность (002) | Один прецедент — одна диаграмма деятельности; шаги потока становятся действиями |
| Деятельность (002) | Последовательность (003) | Действие системы раскрывается в сообщения между объектами; решение — в `alt`/`opt`/`break` |
| Прецедент UC-6 | Состояния (004) | Блокировка элементов, показ расхода, результаты списания — действия `entry` и переходы |
| Последовательность | Состояния | Результаты `ExecuteAsync` (Success, Shortage, исключение) — исходы выбора после «Выполняется» |
| Диаграммы | Классы SDD 003 | Каждая линия жизни — экземпляр класса из 003 |
| Диаграммы | SRS | Каждый прецедент ссылается на `REQ-*` (SRS 5.3) |

Совпадение имён обеспечивается глоссарием; расхождение имён между диаграммой и таблицей прецедентов считается дефектом документации.

## Последствия

- Хорошо: диаграммы версионируются, сравниваются построчно, проверяются в code review; нотация соответствует UML.
- Хорошо: одно правило трассировки «прецедент → деятельность → последовательность → состояния» упрощает контроль полноты.
- Плохо: GitHub не рендерит PlantUML, поэтому рядом с `.puml` хранятся SVG, которые нужно перегенерировать скриптом `docs/uml/render.sh` после каждой правки.
- Плохо: для рендера нужны Java и Graphviz; на ПК кафе они не нужны (только на рабочем месте разработчика).

## Подтверждение

Выполнение подтверждается наличием в репозитории `.puml` и одноимённых `.svg` для каждой диаграммы, ссылками на них из SDD (представления 001, 006, 007, 008) и совпадением имён прецедентов с `docs/use-cases.md`.

## Плюсы и минусы вариантов

- **PlantUML**: полный набор нужных диаграмм, ортогональная маршрутизация, текст; требует отдельного рендера.
- **Mermaid**: рендерится на GitHub; нет дорожек в диаграмме деятельности, слабая нотация UML, нет управления формой линий.
- **draw.io / Visio**: точный контроль внешнего вида; бинарный или громоздкий XML-формат, неудобный diff.
- **CASE-средства**: полная поддержка UML и генерация кода; платные или тяжёлые, избыточны для одного приложения.
