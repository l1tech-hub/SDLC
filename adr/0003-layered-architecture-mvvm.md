# Приложение строится из трёх слоёв (App, Core, Infrastructure) с интерфейсами репозиториев в Core

## Контекст и постановка задачи

REQ-MAINT-001 требует разделить код на слои (интерфейс, логика, доступ к данным), соблюдать соглашения C# и покрыть модульными тестами бизнес-логику: поиск, расчёт расхода, проверку остатков. Часть правил (списание, проверка уникальности, состав блюда) связана с транзакциями БД (REQ-REL-001), поэтому нужно определить, где проходят границы слоёв и как тестировать логику без WPF и без реальной БД.

Как организовать слои и зависимости между ними, чтобы бизнес-логика тестировалась изолированно, а общий объём кода оставался небольшим?

## Драйверы решения

* Модульные тесты бизнес-логики без WPF и без СУБД (REQ-MAINT-001).
* Транзакционные границы в сервисах (REQ-REL-001, REQ-FUNC-015).
* Небольшой объём проекта (16 функциональных требований, один разработчик): архитектура не должна «съесть» сроки.
* Замена слоя хранения или интерфейса в будущем (SRS 3.5.5, A-1, A-2).
* Бесплатные лицензии пакетов (REQ-COST-001).

## Рассмотренные варианты

* Один проект, логика в code-behind
* Три слоя: App / Core / Infrastructure, интерфейсы репозиториев в Core
* Clean Architecture с CQRS и посредником
* Сервисы в Core с прямым использованием `DbContext`

## Итог решения

Выбранный вариант: «Три слоя: App / Core / Infrastructure, интерфейсы репозиториев в Core», потому что только он одновременно позволяет модульно тестировать бизнес-логику без БД и UI (фейки репозиториев), сохраняет простую структуру и закрывает REQ-MAINT-001.

Правила зависимостей: `Core` не ссылается ни на какие проекты решения и не использует WPF и EF Core; `Infrastructure` ссылается на `Core`; `App` ссылается на `Core` и на `Infrastructure` (только для регистрации в DI). Транзакции задаются абстракцией `IUnitOfWork`. Для тестов используются xUnit; интеграционные тесты проверяют ограничения БД на настоящем SQLite.

### Последствия

* Хорошо, потому что правила (поиск, расчёт расхода, проверка остатков, валидация) покрываются быстрыми модульными тестами.
* Хорошо, потому что слой хранения заменяем без изменения бизнес-логики.
* Плохо, потому что требуются интерфейсы репозиториев и небольшой слой преобразования между моделями Core и сущностями EF (если они различаются), то есть немного больше кода, чем при прямом использовании `DbContext`.
* Плохо, потому что слоёв больше, чем нужно для минимального прототипа; дисциплину зависимостей придётся проверять.
* Нейтрально: в качестве MVVM-инструментария и DI выбраны CommunityToolkit.Mvvm и Microsoft.Extensions.DependencyInjection (оба MIT).

### Подтверждение

* Структура проектов и ссылок проверяется в `.csproj`: у `CafeCalc.Core` нет `ProjectReference` и нет пакетов WPF и EF Core.
* Простой архитектурный тест (xUnit): сборка `CafeCalc.Core` не ссылается на `PresentationFramework` и `Microsoft.EntityFrameworkCore`.
* Код-ревью: ViewModel не обращается к БД и файловой системе напрямую.
* Покрытие модульными тестами `Rules/` и `Services/` (REQ-MAINT-001, критерий приёмки).

## Плюсы и минусы вариантов

### Один проект, логика в code-behind

* Хорошо, потому что быстрее всего написать первую версию.
* Плохо, потому что логику нельзя тестировать без запуска окон и БД.
* Плохо, потому что не выполняет REQ-MAINT-001.

### Три слоя: App / Core / Infrastructure, интерфейсы репозиториев в Core

* Хорошо, потому что изолированные модульные тесты и ясные границы.
* Хорошо, потому что транзакции и правила сосредоточены в сервисах.
* Нейтрально, потому что умеренный объём «клея» (интерфейсы, регистрация в DI).
* Плохо, потому что чуть больше кода, чем в варианте с прямым `DbContext`.

### Clean Architecture с CQRS и посредником

* Хорошо, потому что максимальная изоляция и масштабируемость структуры.
* Плохо, потому что для 16 функций и одного разработчика избыточно: много проектов, обработчиков и шаблонного кода.
* Плохо, потому что увеличивает срок и риск относительно выигрыша.

### Сервисы в Core с прямым использованием DbContext

* Хорошо, потому что меньше кода: нет интерфейсов репозиториев.
* Нейтрально, потому что тестируемость возможна через SQLite in-memory.
* Плохо, потому что Core зависит от EF Core, тесты логики требуют БД, и слои смешиваются.

## Дополнительная информация

Связанные требования SRS: REQ-MAINT-001, REQ-REL-001, REQ-FUNC-014…016, допущения A-1, A-2. Связанные представления SDD: 002-composition, 003-logical, 009-patterns, 013-structure, 014-dependency.

Пересмотреть решение, если появится второй интерфейс (например, веб) или заметно вырастет число сценариев; тогда можно рассмотреть выделение отдельного прикладного слоя.
