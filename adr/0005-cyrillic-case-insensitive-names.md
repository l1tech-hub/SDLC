# Регистронезависимые поиск и уникальность названий обеспечиваются приложением (колонка NameKey и фильтрация в памяти)

## Контекст и постановка задачи

Поиск по названию должен находить совпадение по подстроке без учёта регистра (REQ-FUNC-002; то же для блюд и журнала — REQ-FUNC-010, REQ-FUNC-016). Название продукта и блюда должно быть уникальным без учёта регистра (REQ-FUNC-005, REQ-FUNC-011). Интерфейс и данные — на русском языке (CON-9).

Встроенные средства SQLite для регистронезависимого сравнения (`COLLATE NOCASE`, оператор `LIKE`) по умолчанию учитывают регистр только для символов ASCII. Для кириллицы «Мука» и «мука» считались бы разными значениями, а запрос «мук» не нашёл бы «МУКА».

Как реализовать регистронезависимые поиск и проверку уникальности для русского языка?

## Драйверы решения

* Корректность для кириллицы (критерии приёмки REQ-FUNC-002: «мук» и «МУК» находят «Мука пшеничная»).
* Целостность на уровне БД: уникальность должна гарантироваться индексом, а не только кодом (REQ-SEC-001).
* Время поиска ≤ 300 мс при 5000 продуктов (REQ-PERF-001).
* Простота: отсутствие нативных расширений и сложной настройки соединений (REQ-INST-001).
* Тестируемость логики без БД (REQ-MAINT-001).

## Рассмотренные варианты

* `COLLATE NOCASE` и `LIKE` в SQL
* Пользовательская collation и функции SQLite, зарегистрированные в соединении
* Колонка `NameKey` с уникальным индексом и фильтрация в памяти
* Расширение ICU для SQLite

## Итог решения

Выбранный вариант: «Колонка `NameKey` с уникальным индексом и фильтрация в памяти», потому что только он даёт корректную работу для кириллицы без нативных расширений и без настройки каждого соединения, сохраняет гарантию уникальности на уровне БД и укладывается во время отклика при заданных объёмах.

Правила:

* `NameKey = Trim → схлопывание пробелов → ToUpperInvariant()` (единственная функция `NameNormalizer.MakeKey`, SDD 007, алгоритм A1).
* В БД: `NameKey TEXT NOT NULL UNIQUE`.
* Поиск: список загружается в память при открытии вкладки и фильтруется `Contains(query, StringComparison.OrdinalIgnoreCase)` по мере ввода (алгоритм A2).
* Буква «ё» не сворачивается в «е» (см. «Дополнительная информация»).

### Последствия

* Хорошо, потому что корректно для русского языка, быстро и тестируется модульно без БД.
* Хорошо, потому что уникальность гарантирует БД (`UNIQUE`), даже если проверку в сервисе обойдут.
* Плохо, потому что данные дублируются (`Name` и `NameKey`); ключ должен вычисляться только в одном месте (`NameNormalizer`), иначе возникнут расхождения.
* Плохо, потому что поиск не использует индекс БД: все продукты загружаются в память (при 5000 записей — порядка единиц мегабайт, приемлемо); при росте на порядки потребуется пересмотр.
* Нейтрально: сортировка по названию выполняется приложением с учётом культуры `ru-RU`.

### Подтверждение

* Модульные тесты `NameNormalizer` и `NameSearch`: «мук» и «МУК» находят «Мука пшеничная»; очистка поля возвращает все продукты; отсутствие совпадений даёт пустой результат.
* Модульные и интеграционные тесты уникальности: «Мука» и «мука» (а также « МУКА  ») отклоняются; нарушение индекса `UNIQUE` без проверки в коде даёт исключение БД, преобразуемое в ошибку.
* Замер времени поиска на 5000 продуктах (REQ-PERF-001, критерий 300 мс).

## Плюсы и минусы вариантов

### COLLATE NOCASE и LIKE в SQL

* Хорошо, потому что проще всего реализовать и использует индекс.
* Плохо, потому что для кириллицы регистр не игнорируется (только ASCII), что нарушает критерии приёмки REQ-FUNC-002 и REQ-FUNC-005.

### Пользовательская collation и функции SQLite

* Хорошо, потому что сравнение выполняется в БД и работает для кириллицы.
* Плохо, потому что регистрировать нужно на каждом соединении; интеграция с EF Core, миграциями и индексами сложнее.
* Плохо, потому что ошибка в настройке даёт «тихую» потерю гарантий уникальности.

### Колонка NameKey с уникальным индексом и фильтрация в памяти

* Хорошо, потому что корректность для кириллицы, уникальность гарантируется индексом, простая и быстрая реализация.
* Хорошо, потому что логика в `Core` тестируется без БД.
* Плохо, потому что дублирование данных и загрузка списка в память.

### Расширение ICU для SQLite

* Хорошо, потому что полноценная поддержка Unicode в БД.
* Плохо, потому что нативное расширение не входит в стандартную поставку SQLite для .NET, усложняет сборку и установку (REQ-INST-001, REQ-BUILD-001).

## Дополнительная информация

Связанные требования SRS: REQ-FUNC-002, REQ-FUNC-005, REQ-FUNC-010, REQ-FUNC-011, REQ-FUNC-016, REQ-PERF-001, REQ-SEC-001, CON-9. Связанные представления SDD: 004-information, 007-algorithm. Связанные ADR: ADR-0004.

Открытый вопрос к Заказчику (SDD 5.3, DR-7): считать ли «е» и «ё» одной буквой (например, «Мёд» и «Мед»). Рекомендуется да: это сворачивание добавляется в `NameNormalizer` и в `NameSearch` без изменения схемы.

Пересмотреть решение, если число продуктов существенно превысит 5000 или появится потребность в полнотекстовом поиске.
